# Музыкальные транскрипции

Репозиторий для работы над нотными сетками, текстами и отдельными партиями
нескольких музыкальных треков. Каждый трек изолирован в собственном каталоге,
а общие команды сборки находятся в корне.

## Треки

| Основной ID | Алиас | Трек | Партитура |
| --- | --- | --- | --- |
| [MusicBrainz Recording `7402…5533`](https://musicbrainz.org/recording/7402bbda-e0cf-4960-9b85-d8f6f4f85533) | `atom-76--volki-okeana` | Атом-76 — «Волки Океана» | [`score.ly`](tracks/7402bbda-e0cf-4960-9b85-d8f6f4f85533/score.ly) |
| [MusicBrainz Recording `e889…c0f3`](https://musicbrainz.org/recording/e889154d-ae2d-43f0-bd2d-df87d068c0f3) | `moi-rakety-vverh--blown-away` | Мои Ракеты Вверх — «Blown Away» | [`score.ly`](tracks/e889154d-ae2d-43f0-bd2d-df87d068c0f3/score.ly) |

Каталог трека называется по его MusicBrainz Recording MBID. Он однозначно
идентифицирует конкретную запись, к которой относятся таймкоды, аранжировка и
соло. Человекочитаемые алиасы и единственный основной алиас для каждого трека
хранятся рядом с каноническим ID в корневом
[`aliases.json`](aliases.json). Основной алиас используется в путях локальной
сборки. Work MBID хранится в metadata трека и может быть заполнен, если для
абстрактной композиции появится отдельная сущность MusicBrainz.

## Структура

```text
aliases.json                       # алиасы и основной алиас ↔ Recording MBID
.dvc/                              # конфигурация DVC; кеш остаётся локальным
artifact-store/                    # локальный DVC remote, вне Git, в Restic
tracks/
  <musicbrainz-recording-mbid>/
    README.md
    score.ly
    music.ily                      # общие партии трека, если нужны
    dvc.yaml                       # команды и каталог публикуемых артефактов
    dvc.lock                       # хеши зависимостей и результатов
    sources/
      lyrics-with-bar-marks.txt
      solos/                       # LilyPond-источники отдельных партий
    reference/
      README.md
      recordings.json
      audio/
        <recording>.<ext>          # данные в DVC-кеше, не в обычном Git
        <recording>.<ext>.dvc      # Git-указатель на DVC-объект
build/
  <primary-alias>/                 # DVC-выходы и временные эксперименты
```

`flake.nix` автоматически обнаруживает непосредственные подкаталоги `tracks/`,
проверяет совпадение имени каталога с Recording MBID в metadata и создаёт
команды как по ID, так и по алиасу из `aliases.json`. Обе формы команды пишут в
один каталог `build/<primary-alias>/`. Для нового трека достаточно создать
каталог с `score.ly` и `reference/recordings.json`, затем добавить основной
алиас в обе таблицы `aliases.json`. Новый каталог нужно добавить в индекс Git
перед запуском flake-команд, поскольку Nix не включает полностью
неотслеживаемые пути в flake source.

## Воспроизведение артефактов

Основной интерфейс — DVC, запущенный в окружении закреплённого `flake.lock`.
Воспроизвести все отсутствующие или изменившиеся стадии:

```console
nix run .#dvc -- repro --recursive tracks
```

Один трек или одну стадию:

```console
nix run .#dvc -- repro tracks/7402bbda-e0cf-4960-9b85-d8f6f4f85533/dvc.yaml
nix run .#dvc -- repro tracks/7402bbda-e0cf-4960-9b85-d8f6f4f85533/dvc.yaml:render-score
```

DVC сравнивает команды и хеши зависимостей с `dvc.lock`: неизменившиеся стадии
не запускаются, а отсутствующие результаты восстанавливаются из локального
кеша. Проверить состояние и восстановить закешированные выходы без запуска
команд:

```console
nix run .#dvc -- status --recursive tracks
nix run .#dvc -- checkout
```

Граф обеих песен и список стадий:

```console
nix run .#dvc -- dag --dot
nix run .#dvc -- stage list --recursive tracks
```

Именованные публикуемые результаты перечислены в секциях `artifacts` каждого
`dvc.yaml`; используемая версия DVC не предоставляет для них отдельную команду
`list`.

`build/` также используется для одноразовых экспериментов, но долговечными
считаются только пути, объявленные в `outs`/`artifacts` соответствующего
`dvc.yaml`. Необъявленные файлы игнорируются Git и могут быть удалены.

## Низкоуровневые команды

Сборочные блоки DVC доступны напрямую для диагностики. Например:

```console
nix run .#render-atom-76--volki-okeana
nix run .#render-e889154d-ae2d-43f0-bd2d-df87d068c0f3
nix run .#render -- --png -dresolution=144
```

Команды, названные по Recording MBID и по алиасу, выбирают один трек и всегда
используют его канонический локальный каталог `build/<primary-alias>/`. Без
аргументов они копируют PDF и MIDI из той же изолированной Nix-сборки, которую
использует CI. Дополнительные аргументы запускают отдельный диагностический
рендер (например, PNG), не перезаписывая канонические PDF и MIDI.

Проверить все партитуры и metadata в изолированной Nix-сборке:

```console
nix flake check
```

`nix build` собирает общий каталог результатов. Отдельный трек доступен и как
`nix build .#7402bbda-e0cf-4960-9b85-d8f6f4f85533`, и по удобному алиасу
`nix build .#atom-76--volki-okeana`.

Для публикации всех партитур одним каталогом используется отдельный output с
PDF, названными по основным алиасам треков:

```console
nix build .#pdfs
```

PDF и MIDI вместе собираются аналогичным output:

```console
nix build .#artifacts
```

GitHub Actions запускает эту же сборку при каждом изменении `main` и по ручному
запросу. Каждый PDF и MIDI доступен в запуске workflow как отдельный
неархивированный артефакт в течение 90 дней. CI не извлекает DVC-данные и не
скачивает исходные аудиозаписи.

## Происхождение артефактов

Музыкальная идентичность хранится в `reference/recordings.json`: MusicBrainz
Recording MBID обозначает конкретную запись, SHA-256 — конкретный файл, а
`source`/`sourceHint` описывает известный внешний источник. Файлы, переданные
пользователем без проверяемого URL, так и помечены: источник не угадывается.

Техническая цепочка происхождения находится рядом с треком:

- `dvc.yaml` фиксирует точную команду, зависимости и выходы каждой стадии;
- `dvc.lock` фиксирует хеши зависимостей и результатов;
- `flake.lock` закрепляет nixpkgs и тем самым версии LilyPond, FFmpeg, yt-dlp,
  DVC и остальных инструментов;
- `*.dvc` фиксирует хеши невоспроизводимых исходных аудиофайлов, а внешние
  воспроизводимые источники оформляются как выходы стадий в `dvc.lock`; сами
  записи в Git не помещаются.

Например, скачать проверенный YouTube-референс, вырезать соло и построить
сравнение для «Blown Away» можно одной стадией или всем графом трека:

```console
nix run .#dvc -- repro tracks/e889154d-ae2d-43f0-bd2d-df87d068c0f3/dvc.yaml:compare-solo
nix run .#dvc -- repro tracks/e889154d-ae2d-43f0-bd2d-df87d068c0f3/dvc.yaml
```

Проверить, что все аудиореференсы из `recordings.json` присутствуют и совпадают
по SHA-256 и длительности:

```console
nix run .#verify-references
```

## Локальное DVC-хранилище

`artifact-store/` — default DVC remote с относительным путём внутри каталога
репозитория. Он игнорируется Git и самим обходчиком DVC, но входит в регулярный
Restic backup домашнего каталога. Поэтому репозиторий можно перемещать вместе с
хранилищем без исправления абсолютных путей.

`.dvc/cache` остаётся обычным восстанавливаемым кешем. Отправить новые объекты,
проверить полноту remote и восстановить локальные данные можно так:

```console
nix run .#dvc -- push
nix run .#dvc -- status --cloud
nix run .#dvc -- pull
```

Обычная очистка локального кеша не должна затрагивать `artifact-store/`. Не
используйте варианты `dvc gc`, удаляющие данные из cloud/remote, если нет ещё
одной проверенной копии хранилища.
